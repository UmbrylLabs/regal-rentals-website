# Regal Rentals booking backend setup

This feature branch adds Cloudflare Pages Functions, a D1 database, a private admin dashboard, live date-based availability, quote capture, owner/admin logins, and built-in electronic signing.

## Do not merge yet

Do not merge `feature/booking-backend` into `main` until the preview environment has a D1 binding, all migrations, required secrets, an owner account, and completed acceptance testing. The live site remains on the existing manual quote process until then.

## 1. Create the database

In Cloudflare Dashboard:

1. Open **Storage & Databases → D1 SQL Database**.
2. Create a database named `regal-rentals`.
3. Record its database ID.

Using Wrangler from the repository:

```bash
npm install
npx wrangler d1 migrations apply regal-rentals --remote
```

The migrations create the account, customer, inventory, booking, signing, audit, and database protection tables. They also seed:

- 3 × 60-inch round tables at $16
- 2 × 6-foot rectangle tables at $14
- 1 × 10×10 canopy with pricing pending

## 2. Bind D1 to Pages

In the Regal Rentals Cloudflare Pages project:

1. Open **Settings → Functions → D1 database bindings**.
2. Add a binding named exactly `DB`.
3. Select `regal-rentals`.
4. Configure both preview and production environments.

## 3. Add secrets

Create long, unique random values for these Pages secrets:

- `BOOTSTRAP_TOKEN`
- `PASSWORD_PEPPER`
- `IP_HASH_PEPPER`
- `LOGIN_RATE_PEPPER`

Do not commit their values to GitHub. Use different bootstrap tokens for preview and production. Delete or rotate the bootstrap token after the first owner is created.

## 4. Deploy and initialize preview

Deploy this feature branch as a Cloudflare preview. Then open:

```text
https://<preview-host>/admin/setup.html
```

Enter the owner name, email, a password of at least 12 characters, and the preview bootstrap token. The setup endpoint is transactionally locked so only one first owner can be created.

The dashboard is available at:

```text
https://<preview-host>/admin/
```

## 5. Double-booking protection

Inventory is protected in the D1 database itself. Browser checks are only previews.

Statuses that block inventory:

- `hold`, while the hold has not expired
- `confirmed`
- `paid`
- `ready`
- `out`
- `returned`

Statuses that do not block inventory:

- `inquiry`
- `quote`
- `completed`
- `cancelled`
- `expired`

The database rejects:

- creating an overlapping reservation above owned quantity
- activating a quote after another booking took the inventory
- moving a reservation into a conflicting time window
- increasing an active booking above availability
- reducing owned inventory below active reservations
- two simultaneous confirmations for the same remaining inventory

Booking writes use D1 `batch()` operations so related inserts and updates commit together or roll back together. A currently active reservation cannot have its time window or rental items silently rewritten; release it first, edit it, and reactivate it through the conflict check.

Run the safety tests locally:

```bash
npm test
npm run check:js
```

## 6. Electronic signatures

From a booking detail screen, create a private signing link. The signer reviews the agreement, consents to electronic signing, types their legal name, and draws a signature.

Stored evidence includes:

- exact agreement HTML and SHA-256 fingerprint
- agreement version
- typed name
- server-generated signature SVG
- signing time
- IP address and browser information
- evidence SHA-256 fingerprint
- audit-log record

The agreement text generated by `buildAgreementHtml()` is a software placeholder. Replace it with the final Regal Rentals agreement and waiver language and have the final wording reviewed by a California attorney before production use.

## 7. Preview acceptance checklist

- Owner login and logout work
- Failed-login lockout works
- Joe can have a separate admin account
- Public date check displays correct quantities
- Public quote creates an inquiry in admin
- Inquiry does not reserve inventory
- Hold expires and releases inventory
- Confirmed booking blocks overlapping inventory
- Simultaneous conflict test permits only one confirmation
- Cancellation releases inventory
- Inventory cannot be reduced below reservations
- Signing link loads, expires, signs once, and retains evidence
- Mobile public page remains usable
- Security headers are present

## 8. Production release

After preview testing:

1. Apply all D1 migrations to the production database.
2. Configure the production `DB` binding and production secrets.
3. Create the production owner account.
4. Replace the placeholder agreement with final reviewed language.
5. Create a database backup/export.
6. Merge the feature branch into `main`.
7. Perform a real-device smoke test before accepting customer bookings.

Payments, automatic email delivery, password reset, customer accounts, and automatic PDF email attachments are not included in this first backend release.
